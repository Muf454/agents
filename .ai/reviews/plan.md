## MAJOR findings
- P1 (demonstrated): T001 acceptance criterion 4 and the "Mutation check" paragraph, `.ai/tasks.md:17,26`. The task requires both `env['PYTHON_COLORS'] = '0'` in `run_shard` and a `summary()` that strips ANSI sequences before matching `^Ran (\d+) tests?` / `^(OK|FAILED)\b` (today's regexes are at `tests/run_parallel.py:66-67`). Once `summary()` strips escapes, a coloured shard summary parses identically to a plain one, so removing the `PYTHON_COLORS=0` line changes nothing the planned tests observe: exit code 0, `Ran 2 tests`, no `crashed`. The criterion "removing the `PYTHON_COLORS=0` line makes the `PYTHON_COLORS=1` case fail" is therefore unsatisfiable, and the env-isolation half of R1 ("shards run without colour") has no regression test; only the parser does. The implementer will either report a failed mutation check or quietly drop the criterion. Plan change: keep the `summary()` unit test for the stripping, and test the env fix through what the runner does expose: run a *failing* two-test suite (as `test_parallel_runner_failing_test_prints_traceback` does) with `PYTHON_COLORS=1` (host `NO_COLOR`/`FORCE_COLOR`/`PYTHON_COLORS` removed) and assert the echoed shard output (`print(output.rstrip())`, `run_parallel.py:106`) contains no `\x1b[`. On Python 3.14+ `_colorize.can_colorize` returns true for `PYTHON_COLORS=1` before any tty check, so without the env line the echoed output is coloured and the test fails; on older Pythons it is vacuous (record `sys.version_info`). Reword acceptance criterion 4 accordingly ("no escape sequence reaches the shard output under `PYTHON_COLORS=1`"), and make the mutation check remove the env line while this new test runs.

- P2 (demonstrated): T003 implementation notes, `.ai/tasks.md:71`: "the levels from `rejected_rows()[1]` (`{id: level}`)". `rejected_rows()` returns `(head, rows)` where `rows` is a list of `(finding, level, evidence)` tuples (`scripts/lib/workflow.py:1250-1253`), not a dict. - P3 (suspected, medium impact): T004 coverage rule, `.ai/tasks.md:108`. "B ancestor-or-equal of R" is sufficient for `R..X ⊆ B..H` but not necessary. In the ordinary case where master is merged *into* the feature branch between the Claude review and the Codex review, the new merge-base B' is a later master commit, `B' ≤ R` is false, and the rule says "not covered" although the Codex range `B'..H` contains every branch commit of `R..X` (none of them is reachable from B'). Those Claude reviews then stay pending forever, and the pending list the spec wants to shrink does not. Same for a rebase (X vanishes from history), which the plan does not mention either. Plan change: either (a) use the exact containment test, per row: X ≤ H (as now) and `git rev-list --count <R>..<X>` equals `git rev-list --count <R>..<X> ^<B>` (both via `check_output` inside the per-row `try`), which has no false positives and handles the merged-master case, and add that case to the unit test; or (b) keep the rule and state in README/`docs/workflow.md` that merging master into the branch or rebasing it leaves earlier Claude reviews pending until a hand-run `ai-review --base <old base>`.
- P4 (suspected, low impact): T004 parsing, `.ai/tasks.md:105-106`: recheck rows take R = X ("no base"). A Claude re-check examined the parent review's full range (`ai-review:92-96` takes the range from the review header), yet the row is marked covered whenever B ≤ X ≤ H, even when the parent code row in the same log is *not* covered because its base is older than B. The report would then show the parent review pending and its re-check covered, which reads as inconsistent. Plan change: for a `recheck` row, take R from a `code` row with the same HEAD in the same log text when one exists (same parse, no extra git call); otherwise fall back to R = X as planned. Add that pairing to the mixed-row unit test.
- P5 (suspected): T002 test note, `.ai/tasks.md:46`: "Update the one existing assertion … to the new table". In the new column order avg minutes is the last cell, and in `test_runner_logs_task_outcomes_and_report` it is wall-clock time of a real mock run. Specify asserting the row prefix up to the first-time-pass cell (`| sonnet | 1 | 1 | 0 | 1/1 (100%) |`), as the current assertion already stops before minutes (`tests/test_workflow.py:2640`), so the test stays deterministic.
