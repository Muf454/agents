## MAJOR findings
- P1 (demonstrated, carried from round 2 P3): T004 coverage rule, `.ai/tasks.md:109`: "Covered when X ≤ H and B ≤ R". The rule is sound but not complete, and the incomplete case is one this project hits. `.ai/run-log.md:108` records mission control merging `origin/master` into a feature branch to clear PR conflicts. After such a merge the next Codex code review's merge-base B' is the merged master commit (`scripts/ai-review:285-286`), so for every Claude fallback row recorded on that branch before the merge, `B' ≤ R` is false, the row is "not covered", and the report lists it under "Codex catch-up pending" forever, although `B'..H` contains every branch commit that `R..X` saw. The spec (R4) wants pending to mean "no Codex line covers it"; here it would mean "the branch was synced with master once". Round 2 raised this (`.ai/reviews/plan.md:18`) and revision 3 neither adopted it, nor documented it, nor recorded a disposition (`.ai/reviews/dispositions.md` has no round 2 section). Plan change: replace the `B ≤ R` test by the exact containment test, per row inside the same `try`: `X ≤ H` (as now) and `int(git('rev-list', '--count', X, f'^{R}', cwd=cwd)) == int(git('rev-list', '--count', X, f'^{R}', f'^{B}', cwd=cwd))` (`rev-list` exits 0, so `git()` is fine; an unresolvable R still fails `rev-parse` first and skips the row). Add to the mixed-row unit test a code row recorded before a master merge whose later Codex base is the merge's master commit (covered), and keep the existing "base older than B" merged-branch row (still not covered, since its commits are reachable from B). If the author prefers to keep the simpler rule, record the rejection in `.ai/reviews/dispositions.md` with this evidence and add "merging master into the branch or rebasing it leaves earlier Claude reviews pending until a hand-run `ai-review --base <old base>`" to T004's README/`docs/workflow.md` "what stays pending" list.

## Security concerns
None new. `catchup_covers` resolves only cells matching `^[0-9a-f]{7,40}$` with `rev-parse --verify <cell>^{commit}` and runs `merge-base --is-ancestor` (and, with P1, `rev-list --count`) on resolved SHAs, so a committed Markdown row cannot name a ref or inject an option; an ambiguous prefix raises `CalledProcessError` and skips the row. A fabricated row can at most mark as covered an outcome line that exists with that exact project, mode and full HEAD; it cannot add or remove outcome lines. T003 reads the published re-check through the existing verifier, so a hand-edited `recheck.md` yields a line without counts rather than wrong counts.
